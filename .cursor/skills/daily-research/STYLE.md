# daily-research 写作语言（必读）

落盘前读本文。标杆范文：[宝玉《Warp 如何让 Agent 自我进化》](https://mp.weixin.qq.com/s/1YaHaOC1veK3dJhlJyvE9Q)。

## 你要写的是什么

不是说明书，不是会议纪要，是 **读完能带走一个判断** 的技术短文：  
「这件事到底在解决什么失败」「机制上怎么转的」「和我已知的差在哪」。

读者是工程师，愿意看 harness、DPO、Skill——**术语保留**，但句子要顺，像跟人讲清楚，不像填表。

## 宝玉文里值得学的（对照）

| 做法 | 反例（别写） |
|---|---|
| 开头点 **一个问题**（Skill 怎么进化？） | 开头「**一句话**：……」+「这是个啥」 |
| **痛点故事**：试过 A/B 不行，才引出方案 | 一上来列模块表 |
| 小标题是 **话题**（两个 Skill，加上人类反馈） | 小标题是模板（它由什么构成、证据） |
| 术语在 **叙述里** 第一次解释 | 术语表堆在段首 |
| 可夹 **对照经验**（我写过反编译 Skill……） | 全程无人声的百科腔 |
| 原则来自一手源时 **顺述**，不机械编号除非原文就是清单 | 每条事实「一句话+URL+时间」工单体 |
| 结尾自然收束；链接放 **参考** | 「没核实清楚的」独立大段 |

## 推荐结构（灵活用，不要套死）

```text
# <判断句标题>

<1～3 段>：这篇只回答什么；为什么今天值得看；可点名一手来源。

## <痛点或小背景>
以前怎么做、卡在哪（over-ambition、没记忆、sparse reward……用具体失败描述）。

## <机制：只圈 1～2 个问题点>
像讲故事讲环怎么转。harness / Skill / DPO 在句子里出现，第一次顺带解释「它解决哪类失败」。

## <可选：对照、误区、边界>
和相邻方案差在哪；什么还没证实（写进正文一句，别单列「未证实」章节）。

---
**参考**
- [标题](https://完整URL)
```

## 语言

- **短段落**：一段 2～4 句为主；超过 6 行就拆。
- **少列表**：除非原文就是 N 条原则，或必须对比表；机制用 prose 讲。
- **有主语**：谁做了什么、为了什么；少用「可被」「旨在」「层面」。
- **禁止**： lorem、赋能、重磅、一文读懂、日报体、岗位/JD。
- **数字**：只写来源里有的；没有就写「官方没给」。

## 术语

保留英文或行业固定叫法：**harness、DPO、GRPO、PRM、MCP、Skill、TTFT、credit assignment、sandbox、agent runtime** 等。  
不要用「夹具」「执行环」替换 harness。  
第一次出现：用后半句解释，例如「harness——包在模型外的 loop、tool、权限和重试——」。

## 收件箱 vs 深写

- **收件箱**：标题 + 可点链接 + 一句判断，快扫。
- **深写**：按本文写完整短文；语气一致。

## 自检（写完读一遍）

1. 删掉「这是个啥」「一句话」还能读顺吗？  
2. 非工程师同事能听懂 **在解决什么问题** 吗？  
3. 工程师能复述 **机制上的一步** 吗？  
4. 像宝玉那篇，还是像内部 wiki？
