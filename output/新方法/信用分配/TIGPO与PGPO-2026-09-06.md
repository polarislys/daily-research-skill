# 长程 Agent 训练这周在改「失败轨迹里哪一步有功」

形态：新方法  
大主题：信用分配  
日期：2026-09-06（Asia/Shanghai）  
问题点：PGPO 和 TIGPO 各改了信用分配的哪一刀？  
候选：TIGPO、PGPO 尚未晋升到主词表

## 先说清楚

9 月 2–3 日两篇 arXiv，打的是同一块：多轮、稀疏终局奖励时，组内相对策略优化分不清「失败轨迹里哪一步其实是对的」。

**PGPO**（2026-09-02）用组内锚点状态的回报估计势函数，相邻状态的势差给每步打分，失败轨迹内部也能分开好坏。  
**TIGPO**（2026-09-03）批评现有图方法只在当次 rollout 批次建图；它按任务留一张跨更新的转移图，并用 Exploration / Revisit 两档预算重跑旧任务。历史转移只当结构参考，**不进当前 policy loss**。

两篇实验都在 ALFWorld 和 WebShop。这不是已部署产品。

## 问题只圈这些

只讲原理和与 GRPO / GiGPO / GraphGPO 的差。不外推到「该不该上生产」。

## 原理

**credit assignment（信用分配）**：奖励常在整局结束才给 0/1，更新却要落到中间每一步。分错了，会惩罚「方向对但没做成」的动作，也会奖励「瞎走但碰巧成功」的前缀。

**GRPO 家族**：同一任务采一组轨迹，用组内均值方差归一优势，省掉 critic。一组里全失败时，中间步骤仍然糊在一起。

**GiGPO**：把相对优势拆到「同一锚点状态的一组」，仍主要吃最终回报。

**GraphGPO**：把同任务多次转移收成有向图，按到成功终点的最短路给步级分。图只活在当次更新。

**PGPO 多出来的一步**：在组内估计状态的经验势，再用势差当步级优势，并让信用能跨轨迹传。点名的失败是：步级方法若仍绑在**该条轨迹最终成败**上，失败轨迹里的好动作和坏动作一起挨打。

**TIGPO 多出来的一步**：

1. 按稳定 `task_id` 保留转移图，不同策略版本发现的前缀和后缀可以接上。  
2. 固定 rollout 预算切成 Exploration（新采样）和 Revisit（隔一段时间重跑旧任务）。  
3. Revisit 组用当时分数当 detached 参照，稳定小组估计。  
4. 历史 token / log-prob 不回放进损失，避免把过期策略硬塞成 on-policy。

和 GraphGPO 只需两句差：图是否跨更新保留；历史是否进损失。和 PGPO 只需两句差：一个挖失败轨迹内部的势差，一个挖跨更新的图结构。所以两个名字进候选，不并进 `agent-training` 的别名了事。

状态键是隐藏前提。键太细（时间戳、绝对路径）图连不上；键太粗（只留页面标题）不相干转移会并成一点。论文在仿真环境里状态可对齐；仓库级 SWE agent 没有同等证据。

评测侧的伴生约束：静态 SWE-bench 自 2023 公开后容易进训练语料。SWE-rebench 按 issue 创建日对模型发布日标记可能污染。方法涨点如果只发生在旧静态集上，可能是更会背题。这是方法解释的边界，不是本文第二条独立新闻。

实现时有一个工程纪律和论文是对齐的：TIGPO 明确拒绝「把旧轨迹再放进当前损失」。看起来像经验回放，其实只借用图结构和 detached 分数。旧动作的 log-prob 已经过期，硬回放会把 off-policy 偏差写进更新。若复现时图方便起见把历史 token 一并反传，那就不再是这篇论文的方法。

Revisit 也不是「每周刷同一道题涨分」。它是在固定预算里留一档，让新策略有机会把旧前缀接完。只采新票、从不重放上周失败任务，图的左边会永久丢掉。PGPO 没有这档调度，它假定当前组内已经有足够的锚点统计；组很小、又全失败时，势函数本身也不稳。两条方法对「组有多大」的假设不同，不能当成可以随便叠的插件。
