# Temporal 把 harness 拆成「内环你自带、外环我保活」

形态：产品剖析  
大主题：Temporal-Agent-Harness  
日期：2026-09-06（Asia/Shanghai）  
问题点：外层 harness 和 Codex / Claude Code 那种全家桶差在哪？可持久执行具体落在哪些模块上？

## 先说清楚

Temporal 在 2026-08-20 发了早期开源项目 [Temporal Agent Harness](https://temporal.io/blog/temporal-agent-harness-durable-agent-infrastructure)，仓库 [temporal-community/temporal-agent-harness](https://github.com/temporal-community/temporal-agent-harness)。它不重写 agent 循环，而是围在你已经在用的 **inner harness**（OpenAI Agents SDK、PydanticAI、Gemini）外面，把每次 agent 跑成一条 Temporal Workflow。

核心理念写在官博第一句附近：给 agent 能力很容易，给它**责任**很难。责任要的是可强制的策略、靠得住的执行、以及一份说得清「刚才发生了什么」的历史。全家桶 harness（Claude Code、Codex）把循环、上下文、工具、会话一起管了，个人助手够用；一旦 agent 是在替你的生意退款、改地址，身份、授权、业务不变量、失败恢复就不能只写在 prompt 里。SDK 另一端让你什么都能写，但耐久执行、审批挂起、回放得自己砌。Temporal 认的中间层叫 **outer harness**。

项目自我定位早于 public preview，API 会变。本文按官博和仓库 README 拆组成，不把它写成已冻结的生产标准。

## 问题只圈这些

只拆「内外两层怎么接」和「耐久性落在哪几块」。不评 Temporal Cloud 定价，不把 LangGraph / AWS Strands 做成采购表。

## 它由什么构成

**inner harness（内层夹具）**：已经商品化的 agent 循环——模型调用、工具、MCP、结构化输出、一点人在回路。Temporal 点名现成集成：Gemini、OpenAI Agents SDK、PydanticAI。它解决的失败是「每个团队再实现一遍 ReAct」。外层明确不替代这一层。

**outer harness（外层夹具）**：围在内层外面的控制面。官博的对照是：全家桶太大，意见是别人的；SDK 太小，基础设施得自己造。外层提供耐久历史、工具审批策略、turn 编排、类型化接口、Code Mode、回调工具、统一 `AgentEvent` 流。

**Temporal Workflow**：每个 agent 就是一条工作流。事件源记录驱动执行的事件，工人崩溃、发布、停机、闲置很久之后，都能从历史重建状态、从断点续跑。已完成的模型调用和工具调用默认不重跑。这和「进程活着才算 agent 还在」是反的。

**Tool approval policy（工具审批策略）**：模型决定调用能力和能力真正执行之间的缝。默认策略例子：`ToolApprovalPolicy.allow_inherently_safe()`——只读可以自动过，退款一类写操作挂起等人。挂起是耐久的，人隔几小时或几天批了再续，不靠一台机器一直挂着。策略可叠加、运行时改、按工具或会话收窄。

**Turn（轮）**：一次 turn 只调用内层 harness 一次；内层自己的循环可以转很多圈直到进入终端态。终端态不等于整单做完。顾客先问「货到哪了」，再问「能不能改地址」，是同一条长交互上的两轮。turn 也可以由审批到达、定时器、外部系统推送启动，不必须是一句聊天。

**Typed operations**：agent 可以暴露带名字的、有类型的入参出参，而不只是 `string → string`。一个 agent 的操作可以当成另一个 agent 的 toolset。组合走的是应用里那种契约，不是把一段话贴进下一只模型的 prompt。

**Code Mode**：给模型「对已有工具写一段 Python」而不是一轮只挑一个工具。循环、条件、`asyncio.gather` 都可以。关键约束：这段脚本仍走 runner，仍是耐久、可观测、受同一套审批管的 activity，并且跑前按工具签名做静态类型检查。它不是「模型生成的代码扔进黑盒沙箱」。

**Callback tools**：工具不必和 agent 同进程。需要笔记本上的文件、手机摄像头、内网资源时，agent 发出类型化请求，耐久等待外部做完再回来。审批和生命周期仍然走外层。

**AgentEvent**：把轨迹收成结构化事件流——turn、模型交互、工具起止与错误、审批、交接、回复、token 用量。前端画进度、审批服务等人、分析/评测/审计都可以订阅同一条流，而不嵌进循环。换内层 SDK，外层看到的仍是这套事件。回放用的是当时记下的事件，不是事后让模型回忆。

## 理念怎么落进机制

主线：**不可预测的是模型，可预测的必须在夹具里。**

官博举的退款：把「只访问当前顾客、退款要人审」写成说明，作者自己都不安。规则必须施加在执行缝上。Temporal 把这条缝做成 policy + durable wait：模型可以「想退」，执行层可以「先停」。这和 Codex app-server 的审批是同一类问题，只是 Temporal 把停住的时间拉到小时和天，并且停的时候不必占着进程。

另一条可复查的点：Code Mode 若只在沙箱边框做安全，脚本内部的每一次宿主工具调用就会逃出审批。仓库把宿主调用仍派回 runner，当 activity。所以「模型写了 for 循环打 20 个退款」仍然 20 次经过同一策略。这是理念落地，不是演示彩蛋。

`AgentEvent` 不是加在最后的日志。它和 Workflow 的 Event History 是同一地基：没有事件源，谈不上崩溃后续跑，也谈不上「路径本身是产品的一部分」。评测和事故回放吃的是这条流，不是最终一句自然语言答案。

仓库提醒：接口还在改，欢迎提「下一个内层该接谁、策略引擎和身份系统怎么挂」。把它当实验外层，不要当已经冻结的平台 API。
