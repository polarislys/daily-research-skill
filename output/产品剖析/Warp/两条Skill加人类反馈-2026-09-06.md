# Warp 让 Agent 自我进化的不是「模型变聪明」，是两条 Skill 夹着人类评论

形态：产品剖析  
大主题：Warp  
日期：2026-09-06（Asia/Shanghai）  
问题点：Warp 的自进化环由哪几块构成？反馈错了怎么办？

## 先说清楚

Warp 是 2020 年创办的 AI 终端 / agentic 开发环境。Anthropic 在 2026-08-26 的官方案例里把它写成：用 **Claude 平台 + 文件化 Skill**，把本来用完即弃的人类反馈，收成一条会改自己说明书的环。中文侧，宝玉把同一件事收成一个问题——Skill 怎么进化——并对照自己写过的反编译 Skill、写作 Skill：有标准的会越改越好，没标准的会负优化。

核心理念就一句：**人只在原本工作的地方写评论；一条「做事的 Skill」负责执行，一条「改进的 Skill」定期根据评论改前一条。** 改动走普通 PR，人审完才生效。它不是模型在权重里「自己学会了」，也不是再加一段越来越长的系统提示。

本文只拆这一环。Warp 的编辑器、终端复用、定价、和 Claude Code 的会话量，只当背景，不展开。

## 问题只圈这些

1. 这个环由哪些模块拼起来，各自解决哪类失败。  
2. 反馈本身可能是错的，Warp 把闸门放在哪。

不讨论「Skill 要不要写成 200 条命名规则」的全文——那是官方列的 6 条原则，文末只保留和机制有关的几条。

## 它由什么构成

**内层 / 基础 Skill（base skill）**：文件化的程序性知识，写「怎么做 code review / 怎么给 issue 打标签」，不写进每次 prompt。PR 打开或 issue 新建时，对应的 agent 读这份文件再干活。它解决的失败是：agent 不认仓库约定、不认历史教训、你当面纠正过下次还忘。和 **记忆（memory）** 的差别，官方写得很硬：Skill 是稳定的「如何做 X」，跨次运行不变，改动是故意的；记忆是推理时自动写入、一直在变。混用会把临时偏好写进长期规程。

**人类反馈**：不是另填一张问卷。代码审查里，人直接在 PR 或 issue 上写「这条评论有用」或「别建议改这个变量名，我们全局变量用另一套约定」。越具体越好。它解决的失败是：团队已经在 PR 里写下的高质量意见，完全进不了下一轮 agent。初期 Warp 试过人手改系统提示、补 `AGENTS.md`，能好一点，但规模化不了，也用不上日常评论。

**外层 / 改进 Skill（improver skill）**：按日程跑的观察者，不跟每一单任务走。它拉取积下来的人类评论，对照「agent 当时说了什么 / 人怎么回」，然后对**基础 Skill 提一个小补丁**。因为 Skill 就是普通文件，agent 很擅长改它；补丁走 GitHub PR，写明依据哪几条信号、改了哪一段。合并后，下一次内层 Skill 带着新规程跑。

**编排与触发**：官方点名内部编排平台 **Oz**、GitHub Actions、Claude 平台。issue 分诊的例子里：有人提单 → Action 拉起分诊 agent（内层 Skill）→ 人在同一张 issue 下评论 → 定时的「update triage」agent（外层）用 Skill 自带的 Python 脚本把近期带反馈的 issue 收成 JSON，再读回上下文，开 PR。脚本绑在 Skill 里，而不是每次让模型现写爬虫——这就是「渐进式披露」：主文件保持短，细节进资源文件。

**人审**：PR 必须有人批。官方原话是这条环的最后一扣，避免 agent 把错误反馈写进规程。

产品量级（官方案例表，2026-08-26）：融资 7300 万美元；约 80 万月活开发者；Fortune 500 里 56% 用过 Warp；在 Warp 里跑过的 Claude Code 会话累计 1000 万、每周 40 万+；Agent 对话累计 4000 万。这些数字说明环是在真实现网里转，不是演示仓库；它们**不**证明环的质量，只证明有流量可收集反馈。

## 理念怎么落进机制

主线：**反馈必须零摩擦，改进必须可 diff。**

分诊 agent 的一次实转：内层 Skill 给新 issue 打标签、估复杂度、给修复方向。某次它漏了 `ready to spec`（意思是：问题真实存在，即使 UI 还没定，也可以开始写产品和技规）。维护者就在这张 issue 下写清「期望有这个标签，以及为什么」。外层 Skill 稍后跑，从评论里抽出这条信号，开 PR：当 issue 描述的是真问题、即使交互形态未定时，也打上 `ready to spec`。人合并后，下一单继承。

这和「模型自己根据失败日志改自己」差在三处。第一，监督信号来自**人已经在写的评论**，不是模型对模型。第二，写入对象是 **Skill 文件**，能看 diff、能回滚。第三，谁的反馈算数、改哪些字，最后仍是人。宝玉的对照有用：他的反编译 Skill 每次遇到新场景就改自己，能持续变好，但文件会胀；写作 Skill 没有统一标准，经常负优化。Warp 等于把「胀」用渐进式披露压住，把「负优化」用人审和「谁的反馈算数」压住。

官方还把这套环铺到开源仓库的写规格、审查、分诊多个 agent 上，每个环各改各的基础 Skill。改进 Skill 本身被写成可复用模板：去掉领域知识，审查 agent 的 improver 和分诊 agent 的 improver 很像。所以他们建议力气多花在 improver，而不是给每个任务重写一套进化逻辑。

反馈错了怎么办——官方当默认会发生，不盲收：

- 给 agent 足够上下文做合理性检查  
- 限制谁的意见能改 Skill（不是全员投票）  
- 终审或过滤至少一处留人  
- 有标准答案的领域（测试过不过、部署成不成）先建验证集，让 agent 对基准打  
- 没标准答案的领域（风格、文档）只收领域专家，不要对所有人开放

和机制直接相关的几条原则，不再展开成鸡汤：写原则不写死规则；解释为什么；在人已经工作的地方收反馈；Skill 保持短、用引用而不是把全书塞进上下文；少量高质量评论胜过一堆赞踩。
