# Warp 的自我进化，靠的是两条 Skill 和人类在 PR 里的评论

Anthropic 刚写了 Warp 怎么用 Claude 做 [self-improving agents](https://claude.com/blog/how-warp-builds-self-improving-agents-on-claude)。我读完觉得它真正在答一个问题：**Skill 怎么进化？** 不是模型权重偷偷更新，也不是聊天记录越来越长。

宝玉之前拆过同一篇官方案例，还对照过自己写的反编译 Skill：有标准、能改文件的会越改越好；写作 Skill 没统一标准就经常负优化。Warp 的做法，就是把「进化」锁在 **Skill 文件 + PR** 上。

## 痛点：Agent 审查代码，但记不住你们家的规矩

Warp 在终端场景里做 Code Review。一开始让 Agent 直接 review，效果一般——不了解项目、不知道团队规范，你当面纠正，下次还是忘。说白了就是 **没有可继承的程序性知识**。

他们试过改系统提示、补 `AGENTS.md`（有意思的是 Claude 官方案例里写的是 `AGENTS.md`），但两件事卡住了：得有人持续手工维护；更浪费的是，工程师在 PR 里已经写了很多高质量评论，完全进不了下一轮 Agent。

## 两个 Skill，加上人类反馈

解法很具体：

- **base Skill**：负责干活（审查、分诊 issue），规程写在文件里。  
- **人**：不填表，就在 PR/issue 下正常评论。  
- **improver Skill**：定时跑，把「Agent 当时说了啥 / 人怎么回」对上，给 base Skill **提一个小补丁**。  
- **PR + 人审**：补丁合并才生效。

换句话说，不是模型自己改自己，而是 **Agent 根据人类对结果的标注，去改 Skill 文件**。摩擦力故意做低：人只在本来工作的地方写字，后面收集、开 PR 由 **harness**（GitHub Actions、内部 Oz 等）编排。

这和 **memory** 要分开：memory 是运行时自动写、一直在变的；Skill 是稳定规程，改动是故意的、可 diff 的。

## 反馈错了怎么办

Warp 默认反馈会错，所以不盲收：限制谁能影响 Skill；始终留人审；有客观标准的（测试过不过）先建小 benchmark；风格类只靠领域专家，不开放全员投票。

官方案例里还列了六条原则，和机制最相关的两条是：**反馈要在人本来工作的地方收**；**improver Skill 本身可以复用**——审查 Agent 的 improver 和分诊 Agent 的 improver 很像，力气花在 improver 上，而不是每个任务重写一套进化逻辑。
