# Claude Managed Agents 把 harness 做成托管运行时，脑和手只在需要时接线

形态：产品剖析  
大主题：Claude-Managed-Agents  
日期：2026-09-06（Asia/Shanghai）  
问题点：「脑手分离」具体拆成哪些接口？为什么能降 TTFT？

## 先说清楚

Anthropic 在 [Scaling Managed Agents](https://www.anthropic.com/engineering/managed-agents) 中把 **Managed Agents** 描述为 Claude 平台上的托管服务：跑 **长时程、异步** 任务，会话可持续数小时；harness（循环、工具路由、上下文压缩、错误恢复）由 Anthropic 维护并随模型迭代更新。

核心理念是 **decoupling the brain from the hands**：**brain** = 模型 + 决定下一步的 harness；**hands** = 真正执行的工具与沙盒。容器不是会话开始就常驻，而是 brain 通过工具调用 `execute(name, input) → string` **按需申请**。没有立即需要隔离执行时，推理可以先于容器就绪启动——官方称 p50 TTFT 降约 60%、p95 降超 90%。

本文只拆「脑手分离 + 按需沙盒 + 会话日志」三块，不展开计费细则与各云区域。

## 问题只圈这些

1. 接口层固定了什么、刻意不假设什么？  
2. 旧 harness 假设如何随模型升级而「减值」？

## 它由什么构成

**会话日志（session）作为状态源。** 连接断开可从 durable event log 恢复；工具调用与失败可追踪。解决的失败是：长任务中途网络抖动导致整单重跑。这和 **agent runtime**（一次跑起来的进程 / 状态 / 工具总线）的关系是：runtime 语义被托管化，开发者不自己拼进程监督。

**按需沙盒（hands）。** 只有需要隔离执行时才 provision 容器；否则 orchestration 层先消费 pending events 启动推理。解决的失败是：每个会话开头空等镜像 / 容器，拉长首 token 时间。

**可扩展的多 brain。** 扩并发 = 启多个无状态 harness，必要时再接 hands。解决的失败是：单进程 harness 把调度与执行绑死，横向扩容要复制整套环境。

**Meta-harness 定位。** Managed Agents 被形容为 **unopinionated about the specific harness**：Claude Code 是一种 harness，领域特化 harness 也可以接入；平台只坚持「能操纵状态（session）+ 能算（sandbox）+ 能安全地多脑多手」。这和「把 Claude Code 架构抄一遍」不同——接口稳定，内部环可换。

**随模型更新的 harness 维护。** 二手解读（EvoMap 等）引述：为 Sonnet 4.5 写的 **context reset** 是为缓解「context anxiety」；换 Opus 4.5 后该焦虑减轻，旧 reset 反而拖后腿——因此托管 harness 的价值之一是 **由供应商负责拆掉过时假设**。机制上可复查的一点：**harness 组件应视为对「模型当下做不到什么」的假设，模型升级后假设可能作废。**

## 理念怎么落进机制

主线：**先能推理，再按需伸手。**

长时程任务（读仓库 → 计划 → 改代码 → 测 → 开 PR）适合 Managed Agents；短同步问答仍用 Messages API。边界清晰：要小时级自治与工具编排，买托管环；要单次补全，不必背会话小时费。

与 OpenAI「环境即 harness」（仓库 + CI 约束）对照：Anthropic 这边把 **环本身** 托管，客户少维护 runtime；OpenAI 更强调客户仓库内的机械约束。两者都承认 harness 不会消失，只是 **重心迁移**（编排 vs 环境）。
