# OpenAI 的 Harness Engineering：工程师改的是环境，Codex 改的是代码

[这篇官方长文](https://openai.com/index/harness-engineering/) 在讲一件反直觉的事：一支小团队几个月做出很大的内部产品，**业务代码几乎全是 Codex 写的**；人很少直接改源码，而是设计 **harness**、下任务、审 PR。

如果你关心「Agent 时代工程师还剩什么」，值得读；这篇只拆 **环境怎么当 harness**。

## 瓶颈从写代码变成验代码

吞吐上去以后，卡脖子的是人做 QA。OpenAI 的应对不是加人，而是让 **日志、指标、UI** 对 Codex 像对工程师一样可读——prompt 可以从「帮猜 bug」变成「按 PromQL 拉曲线再定位」。也就是说，harness 工程包含 **可观测性也要 Agent 能读**。

## 三个硬机制

**每个任务一间屋**：git worktree 隔离，旁边挂临时 observability（log / metric / trace），Agent 用 LogQL、PromQL 自查。

**规矩进 repo**：`docs/` 放架构和规格；`AGENTS.md` 只做目录，别把全书塞进上下文。CI、linter、结构测试 **机械拦** 坏合并——enforce invariants，不要 micromanage 每个函数。

**PR 上自审 + agent review**：Codex 本地看 diff，再拉 cloud agent review，评论改到过关再请人。人不再是唯一 QA。

OpenAI 有句话很硬：**从 Agent 视角，上下文里没有的东西就等于不存在。** 所以验收方式也得进它能读的环境。

## 和 Anthropic 长任务 harness 差一眼

Anthropic 常拆 Planner / Generator / Evaluator 多角色互盯；OpenAI 这篇更强调 **代码库 + CI 的约束力**。共同点都是：模型变强后，旧 harness 假设会过时（比如为 context anxiety 写的 reset），接口要能换。
