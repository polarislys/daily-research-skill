# OpenAI 的 harness 重心不在「多几个 agent」，而在把仓库变成可机器验收的环境

形态：产品剖析  
大主题：Codex  
日期：2026-09-06（Asia/Shanghai）  
问题点：Harness Engineering 把哪些约束写进环境，而不是写进 prompt？

## 先说清楚

OpenAI 在 2026 年初的 [Harness engineering](https://openai.com/index/harness-engineering/) 博文里描述：一支小团队用 **Codex agent** 在约五个月里交付了一个百万行级内部产品，**应用逻辑、基础设施、文档和可观测性代码均由 agent 写出**；人几乎不直接改源码，而是通过 prompt 描述任务、让 agent 开 PR，并设计让 agent 能自己验收的环。

这和「又一个能写代码的 CLI」的差别在于：**harness（夹具）** 被定义成包在模型外的整套约束——工具、权限、文档结构、反馈环、隔离环境——把「不稳定的大模型输出」收成可合并的 PR。OpenAI 的表述是：从 agent 视角看，**上下文里拿不到的东西就等于不存在**；所以工程重心从手写代码转向设计环境、写清意图、造可自动跑的验收。

本文只拆「环境即 harness」这一刀，不重复本文件夹另一篇关于 Codex 开源三层接入的叙述。

## 问题只圈这些

1. 哪些机制被 deliberately 写进仓库 / CI / 观测栈，而不是每次 prompt 里重复？  
2. 隔离与可查询性如何支撑「agent 自审 PR」？

## 它由什么构成

**任务隔离：git worktree + 临时观测栈。** 每个任务在独立 worktree 里跑，配套本地日志 / 指标 / 链路（文中举例可用 LogQL、PromQL 查询）。解决的失败是：多 agent 并行改同一棵树互相踩、以及「改了代码却看不见运行时行为」。worktree 是物理边界，不是 prompt 里的「请注意不要改别的分支」。

**仓库即系统记录（system of record）。** 架构图、执行计划、规格说明放进结构化 `docs/`，用交叉链接和索引让 agent 能检索。`AGENTS.md` 被设计成**目录页**（官方建议约百行量级），指向更深文档，而不是把全书塞进上下文。解决的失败是：知识只存在于聊天历史，换会话就丢。

**机械约束代替口头规范。** 自定义 linter、结构测试、依赖分层规则写进 CI；PostToolUse hook 在工具调用后做确定性检查。解决的失败是：agent 口头「遵守架构」却在边界处抄捷径。OpenAI 明确倾向 **enforce invariants, don't micromanage**——卡死不变量，不把每个函数怎么写写死。

**PR 闭环：自审 + 他审 + 迭代。** 人下发任务后，Codex 本地自审 diff，再在云端拉其他 agent review，根据评论改到「所有 agent reviewer 满意」再请人看。人称这是 Ralph Wiggum Loop 的工程版。解决的失败是：吞吐上去后人成为 QA 瓶颈——于是把 UI、日志、指标也做成 **agent 可读**，让「查 800 条重复日志」类任务在环内完成。

**标准工具面，不造私有胶水。** agent 直接用 `gh`、仓库内嵌 skill、本地脚本拉上下文，避免人复制粘贴进 CLI。这和 MCP / skill 文件化是同一族思路：可组合、可 diff。

## 理念怎么落进机制

主线：**约束放在环境里，验收放在环里。**

当代码产出速度是人工的约十分之一时，瓶颈变成人类 QA。OpenAI 的应对不是加人，而是让 **应用 UI、日志、指标** 对 Codex 像对工程师一样可查询；prompt 从「帮我猜 bug」变成「按 PromQL 条件拉曲线再定位」。这意味着 harness 工程包含 **可观测性产品设计**，而不只是 agent loop。

与 Anthropic 同期「多 agent 互相监督」的 harness 路线对比（见 Zenn 等二手综述）：OpenAI 这边更强调 **代码库与 CI 的约束力**；agent 数量不必膨胀，但 **环境必须能拒绝坏合并**。两种路线都承认：模型变强后，旧 harness 假设会过时（例如为「context anxiety」写的 reset 逻辑），需要可替换的接口层——OpenAI 用仓库规范 + 机械测试承载这种可替换性。
