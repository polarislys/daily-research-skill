# 长程 Agent 训练这周卡在「失败轨迹里的哪一步有功」

日期：2026-09-06（Asia/Shanghai）  
问题点：TIGPO、PGPO 都在改 credit assignment（信用分配），这和换一个更大的 SFT 数据集有什么不同？评测被污染之后，训练岗该先接哪一层？  
关键词：agent-training, long-horizon, post-training, agent-eval, regression-eval  
候选（尚未进主词表）：TIGPO, PGPO, credit assignment

## 结论

9 月 2–3 日连续两篇 arXiv，题目不同，打的是同一块骨头：**多轮、稀疏奖励**时，组内相对策略优化（GRPO 一类）分不清「失败轨迹里哪一步其实是对的」。PGPO（2026-09-02）用组内锚点状态的回报估计**势函数**，让相邻状态的势差给每步打分，失败轨迹内部也能分出好坏。TIGPO（2026-09-03）批评现有图方法只在**当次 rollout 批次**建图，换一轮更新就把图扔掉；它给每个任务留一张跨更新的转移图，并用 Exploration / Revisit 两档预算把「以前走过的任务」再跑一遍，历史转移只当结构参考，**不进当前 policy loss**。

对 Agent 训练与优化岗，这不是再追一个方法缩写。这是在问：你们的后训练是不是还在用「整条轨迹一个标量」更新所有 token。下一步是 **训 + 评**：先保证轨迹里有步级日志，再决定用势差还是用图距离；评测侧则不要只报 SWE-bench 静态集。

## 问题界定

只讨论长程 agent 的**信用分配**，以及它为什么倒逼评测活起来。  
不讨论通用 RLHF 配方，也不把 TIGPO/PGPO 写成已晋升关键词——它们是本周论文自造名，先记 candidates。

## 第一层：对象是什么

**credit assignment（信用分配）**：奖励往往在整局结束才给 0/1，训练却要更新中间每一步。分错了，会惩罚「方向对但最后没做成」的动作，也会奖励「瞎走但碰巧成功」的前缀。PPO 靠学一个 value 函数估优势；GRPO 用同一题的一组样本做相对归一，省掉 critic，但一组里全失败时，中间步骤仍然分不开。

**agentic RL / 后训练**：在可交互环境里对策略做强化学习或偏好优化，而不是只做单轮 SFT。环境必须能重置、能验真（测试、页面、模拟器）。ALFWorld（家务仿真）和 WebShop（购物站）是这两篇的共同试验田——因为步数长、中间几乎没分。

**PGPO（Potential-Guided Policy Optimization）**：组内先估计状态的经验势，再用相邻状态势差当步级优势，并让信用能跨轨迹传。论文强调：GiGPO 等步级方法仍绑在**该条轨迹最终成败**上，于是失败轨迹里的好动作和坏动作一起挨打。PGPO 要解决的就是这块。提交时间 2026-09-02。

**TIGPO（Temporal Instance-Graph Policy Optimization）**：在 GraphGPO 这类「把转移收成图、按到成功节点的距离给分」之上，把图做成**按任务持久**。早期策略可能走出好前缀，后期策略可能从重叠状态走完；若图随 batch 丢掉，这两段接不上。TIGPO 还把固定 rollout 预算切成 Exploration（新采样）和 Revisit（隔一段时间重跑旧任务），并用当时的分数当 detached 参照，稳定小组估计。历史 token / log-prob **不回放进损失**，避免 off-policy 硬套。提交时间 2026-09-03。

**GiGPO / GraphGPO（本文只当对照，不新开词条）**：GiGPO 把相对优势从「整局一组」拆到「同一锚点状态的一组」，仍主要吃最终回报。GraphGPO 把同任务多次 rollout 的转移收成有向图，按到成功终点的最短路给步级分。TIGPO 认为后者仍然 **batch-local**：这张图只活在当次更新。能用两句中文说清差别——「图是否跨更新保留、历史是否进损失」——所以 TIGPO 记入候选，而不是并进 `agent-training` 的别名了事。PGPO 的差别是「失败轨迹内部有没有独立于最终 0/1 的步级信号」，同样够资格单独观察。

**agent eval 与污染**：静态 SWE-bench 自 2023 公开后，后训练语料很容易见过原题。SWE-rebench 的做法是持续从 GitHub 挖新 issue，并按「issue 创建日 vs 模型发布日」标记可能污染的评测。它不是本周新论文，但是训练岗必须并排看的评测夹具：你若用旧静态集调参，PGPO/TIGPO 的增益可能只是「更会背题」。SWE-rebench 自己也承认自动挖题不如人工 Verified 集「道道可解」，所以线上成功率偏低不一定等于模型变差，可能是题脏。回归评测要同时看 **pass@k** 和 **成本**，只看平均解决率会被「多采样碰运气」抬上去。

过去 24–72 小时具体出现了什么：两篇可打开的预印本，实验都在 ALFWorld / WebShop，都声称相对近期的组方法有增益。没有出现可核对的官方训练产品发布。方法名 TIGPO、PGPO 本日按探索通道入账，不晋升。

## 第二层：机制与岗位含义

主线是训练闭环，附带评测约束。

先分清你们现在处在哪一档，再抄论文：

1. **只有最终 0/1**：整条轨迹一个优势。换模型或加 SFT 都可能看起来「涨点」，其实是最后一步碰巧对了。
2. **组内相对（GRPO 家族）**：同一任务多采几条，用组均值方差归一。便宜，但对「全失败组」束手。
3. **步级但仍绑最终成败**：失败轨迹内部仍然糊成一团。PGPO 点名的就是这里。
4. **图 / 跨更新结构**：用状态合并把不同轨迹接到同一张图。TIGPO 进一步让图活过一次更新，但实现成本是：稳定的任务 id、状态哈希、以及「历史只作参照」的工程纪律。

岗位动作不要从「复现 TIGPO」开始。没有可对齐的状态表示，图是建不起来的；没有步级日志，势差也算不了。状态键本身就是设计问题：键太细（含时间戳、绝对路径），图永远连不上；键太粗（只留页面标题），不相干的转移会被并成一个节点，信用会漏到错误动作上。先从「规范化 URL + 关键 DOM 文本」或「仓库相对路径 + 测试失败摘要」这种人类也能复核的键做起。

TIGPO 的 Revisit 对工程也有直接含义：固定预算里留一部分重跑旧任务，不是为了刷同一题的分数，而是让新策略有机会把旧前缀接完。你们若每周只采新票、从不重放上周失败单，就等于把图的左边永久扔掉。这和业务上的「失败工单回放」是同一纪律，只是训练里要写成采样器，而不是靠人点。

**明天能做的一个动作**：在你们现有的一条 agent 训练或回放流水线上，强制每步落这些列——`task_id`、`step`、`state_key`（哪怕只是规范化后的 observation 哈希）、`action`、`episode_return`。先用 50 条失败轨迹做一张表：哪些 `state_key` 在成功轨迹里也出现过。这张表就是「失败里有没有好前缀」的最低证据。有了它，再决定是上势差、上图，还是先修环境重置。同一天把评测脚本加上「题的创建日」，凡是早于当前模型发布日的题，分数旁边打 `possibly-contaminated`，先别拿去向老板报喜。

评测侧配套：把对外数字从「SWE-bench Verified 一次分数」改成「冻结脚手架 + 带时间戳的题集」。SWE-rebench 的 live 榜把污染标出来，就是在逼训练岗承认：涨点来源必须能说清是泛化还是见过题。脚手架（harness）不冻结时，模型分数和环分数会搅在一起——这正好接回今天第一篇：没有环的版本号，训练曲线不可读。
