# Hermes 把「会学」写进了 runtime，而不是等下一轮训练

这篇只答一个问题：Hermes 标榜的 built-in learning loop，和 Warp 那类 skill evolution 到底是不是一回事。2026 年的 agent 产品正在分岔——有的在改权重，有的在改磁盘上的文件；若把两者混为一谈，harness 的架构选择很容易选错方向。

## 痛点：Agent 会做事，但不会「留下」

你大概经历过这种挫败：同一个 agent 第三次帮你部署 staging，仍然不记得上次踩过的端口冲突；或者它刚在对话里摸索出一套可行的 PR 流程，新开 `/new` 后一切归零。更隐蔽的问题是：你把 workflow 写进 Skill 之后，环境变了——API 废弃、CLI 换参数——Skill 不会自己改，除非有人再跑一轮蒸馏或手改 Markdown。

业界补救路线大致三条：把一切都塞进 system prompt（token 贵、噪声大）、外挂向量 RAG（检索到段落，不等于可执行步骤）、离线把轨迹蒸馏成 Skill 再人工审核（慢、且与在线体验脱节）。2026 年论文里还有 MASkills 一类思路：优化对象是各 agent 的 SKILL.md 而不是权重——但仍偏离线批处理。

Warp 代表第四条路：用真实轨迹上的 preference 信号做 DPO，让**模型权重**在训练环里进化——那是 skill evolution 的「重工业版」，需要数据管线、偏好标注、回归评测。Nous Research 的 Hermes Agent 则走**运行时进化**：默认不动 logits，动的是 harness 外的持久化状态——memory 文件、skill 目录、会话索引，以及一轮对话结束后的 background review。它还集成了 Honcho 做 dialectic user modeling，跨 session 加深「你是谁」的模型——这与 memory 的硬字符上限互补：一个管结构化画像，一个管可编辑的显式笔记。

README 用一句话概括差异：「The only agent with a built-in learning loop」。关键不在 slogan，而在环是否**闭合**：反馈从哪进、写到哪里、下一 session 怎么读回来、人能否 veto。

## 机制：三环怎么转

**第一环——有界记忆（memory）。** 两个文件：`MEMORY.md`（约 2200 字符）存环境事实与教训，`USER.md`（约 1375 字符）存用户画像。会话启动时它们被**冻结**注入 system prompt——这是刻意的 prefix cache 优化；会话中的增删改用 `memory` 工具，变更立即落盘，但要到**下一 session** 才进入 prompt。写满时工具返回错误，agent 必须 consolidate 或删除，不能静默截断——这种「硬顶」迫使 agent 做信息密度压缩，而不是无限堆叠流水账。memory 的定位是「每轮都该在场的小事实」：部署命令、机器 quirks、用户讨厌 verbose 回复。写入前还有 injection 扫描， block 凭证外泄与 prompt 注入模式，因为 memory 会直接进 system prompt。这与 Skill Imitation Trap 论文提醒的「只从成功轨迹蒸馏会越检索越敢调错工具」形成对照：Hermes 把失败教训也鼓励写进 memory/skill，但靠 write_approval 让人类兜底。

**第二环——按需 Skill（程序性记忆）。** 长流程、多步骤 SOP 不进 memory，进 `~/.hermes/skills/` 下的 `SKILL.md`，兼容 agentskills.io 开放标准。Progressive disclosure 控 token：`skills_list` 只暴露 name/description（约 3k token 量级索引），真正需要时才 `skill_view` 全文；大 skill 还可 `skill_view(name, path)` 只读某个 reference。Skill 内容规范强调写 **lesson 不写 log**：pitfall 要是可泛化规则加机制说明，不要 PR 号流水账——否则 background review 会把噪声固化成「假技能」。Agent 通过 `skill_manage` 创建、patch、维护 skill；`patch` 优先于 `edit`，只改 delta，省 token 也省 review 成本。用户用 `/learn` 从本地 SDK 目录、URL 或「刚才那套部署流程」蒸馏 skill——大语料（整本书、论文栈）会落成 knowledge-base skill：瘦 `SKILL.md` 做索引，`references/` 按章存放，查询成本跟答案深度成正比，不是跟源文件大小成正比。

**第三环——回合后 background review。** 每轮对话结束，Hermes 可在辅助模型（默认与主模型相同，可配 `auxiliary.background_review` 换便宜模型）上跑自审：重复的 user 纠正、刚跑通的多步 workflow，被压成 memory 条目或 skill patch。官方 benchmark 称换 Flash 类模型做 review 可省约三到五倍成本，且 memory capture 一致、skill capture 近一致——因为它 replay 的是已 warm 的主对话 cache，或 fork 时 replay 紧凑 digest。默认静默写入；若开 `memory.write_approval` / `skills.write_approval`，写入进 staging，用 `/memory pending`、`/skills diff` 人工放行——这是 **consent-aware** 学习，不是黑箱自改。Skill 体积大，staging 一律走 diff 审查，不像 memory 可在 CLI 里 inline 读全文。`display.memory_notifications` 控制是否在 Telegram 里弹「💾 Memory updated」。Cron 与 messaging gateway 上的 unattended job 同样继承这套环：复杂任务结束后可 autonomous 建 skill，但 approval gate 对后台 review 同样生效。

此外 `session_search`（SQLite FTS5）提供无限容量的「上周聊过什么」——与 memory 分工：memory 固定占 ~1300 token/session；session 搜索按需、无 LLM summarization 成本，返回 DB 里原始消息而非二次摘要，避免「搜到了但被模型概括错」。`/journey` 把 skill 与 memory 节点画成时间线，支持 delete/edit，learning 不再是黑盒目录里的 hidden files。

三条环的边界：**memory 是常量上下文，skill 是条件加载的可执行文档，session 是可搜索的原始轨迹。** 相对 Warp/DPO：Hermes 改的是文件系统状态，不是 loss 里的 preference pair；进化粒度是「一条 pitfall 规则」或「deploy 步骤 3 用这条命令」，不会自动泛化到新 base model——换 provider 后 skill 仍可读，但「肌肉记忆」不随权重迁移。相对纯 Skills Hub（装完不变）：Hermes 多了 curator 式维护、background review、`/journey` 可视化学习时间线，接近「个人 runbook 会自己长」。

项目级 skill（`.hermes/skills/`、`.agents/skills/`）有 trust + 安全扫描 quarantine；curator **不会**改 repo 内 skill，agent 新建 skill 默认进 `~/.hermes/skills/`，避免 clone 来的恶意 SKILL.md 被自动 patch。

## 和 Warp / MASkills 放一起怎么选

若你在做 **团队级** skill 进化（PR 审 Skill、DPO 训权重），Warp 或 MASkills 那条路更合适：变更可 code review、可进 CI。Hermes 适合 **个人或单租户** 长期驻留：Telegram 上纠正一次部署，回 CLI skill 已更新。两者可以并存：Hermes 当 daily driver 收集 pitfall，定期把成熟 skill 提 PR 进团队仓库——但别指望 Hermes 的 background review 自动产生能过合规的 enterprise skill，默认仍要 `write_approval`。

Learning loop 的评测标准也不同于 benchmark 分数：看 **重复纠正次数是否下降**、skill 文件 git diff 是否可解释、误写入是否被 approval 拦住。Honcho 画像 + memory 硬顶 + skill progressive disclosure，本质上是在 **固定 context 预算** 下做 curator——这对 2026 年 context 变长但不免费的现实很务实：不是无限堆历史，而是把「该每轮在场」和「该按需加载」分开。

## 对照、误区与边界

和 OpenAI Codex-as-platform、Temporal outer harness 比，Hermes 偏**个人/小团队长期驻留 agent**：七种 terminal backend（local、Docker、SSH、Modal、Daytona…），Telegram 网关，$5 VPS 可跑；subagent 并行、Python RPC 把多步 pipeline 压成零 context 成本的 turn。和 Claude Managed Agents 比，Hermes 不做托管式 brain/hands 分离，learning 完全本地文件，数据驻留自控；与 Temporal 的 AgentEvent 流比，Hermes 的轨迹在 SQLite 与会话文件里，缺少 workflow 级 durable turn——个人场景够用，金融级 audit 可能要外接。

常见误区：把 `/learn` 当成 RAG 索引——它产出的是** procedure 文档**，不是 embedding 库；Karpathy LLM Wiki  bundled skill 才是「编译型知识库」，与 learning loop 是不同模式。另一误区：以为 background review 等于训练——没有 gradient，只有「是否写入 memory/skill」的决策。第三误区：把 agentskills.io 兼容当成「Skill 会跨产品自动进化」——格式可移植，Hermes 的 review/curator 逻辑不跟着走。

Research 向用户还会用到 trajectory 生成与压缩导出——那是给**下一代 tool-calling 模型**造训练数据，与在线 learning loop 又是分开的按钮：一个服务 research，一个服务 daily driver。

若你关心可审计性，应默认打开 write_approval，把 learning loop 当「建议引擎」。Skills Hub 从 skills.sh、well-known、GitHub tap 安装的 skill 带 quarantine 扫描与 lock.json 审计链——learning 不只靠 agent 自写，也靠外部 skill 生态；但 Hub 装进来不会自动触发 background review，除非 agent 在使用过程中 patch。

Gateway 跨 Telegram/Discord 与 CLI 共享同一 Hermes home 时，learning 是统一的：在手机上纠正部署流程，回 CLI 后 skill 已在磁盘上——这是「跟用户一起长大」的产品承诺的落地方式，不是 marketing。代价是你要管理 `.hermes` 备份：evolution 在文件里，丢目录等于丢经验。

可带走的一句判断：**Hermes 的 evolution 发生在 harness 外的文件层，Warp 的 evolution 发生在 harness 内的权重层——前者便宜、可 diff、可回滚；后者泛化强、infra 重。选哪条，取决于你优化的是个人 agent 的可维护性，还是 base model 的下一次发布。**

举一个 background review 如何闭合 learning loop：你在 Telegram 纠正「staging 部署要用 `docker compose -f docker-compose.staging.yml` 而不是默认文件」——当轮对话结束，auxiliary 模型 replay 主对话 cache，把这条压进 `deploy-staging` skill 的 pitfall 段，或写入 `MEMORY.md` 的「环境事实」槽。下一会话 `/new`，冻结的 memory 与 skill 索引已含修正；若开了 `skills.write_approval`，改动先进 staging，你用 `/skills diff` 看 delta 再放行——与 Warp improver 开 PR 同构，只是 **个人租户默认静默、企业可强制 gate**。Cron 触发的 unattended job 跑完长任务后同样走这套环：complex workflow 结束 → background review → skill patch，approval 对后台同样生效。Honcho 画像管「你是谁、偏好什么 verbosity」，memory 硬顶管「每轮必带的小事实」——二者分工避免把用户传记塞进 procedure Skill。

与 DPO 路线对照：Hermes 不训 preference pair，但 **人类纠正就是 preference signal**；差别在 signal 写进 SKILL.md 而非 loss。你若把 Hermes 当 daily driver、Warp 当 org 级权重进化，成熟 skill 可 PR 进团队 repo——personal pitfall 收集 → 文件 diff → 合规 review → 共享 Skill，这是 2026 年常见的 **双层进化**：文件层快迭代，权重层慢泛化。评测 learning loop 不看 benchmark 分，看 **同一部署任务重复纠正次数是否下降**——这比 MMLU 更贴 harness 价值。
